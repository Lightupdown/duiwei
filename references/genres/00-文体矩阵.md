# 文体矩阵：不同场景的「去 AI 味」标准

项目起点（2026-10-19）：**「不是所有场景都能用一套去 AI 味的提示词去改。写公众号、写文章、润色语言、发公告、发通知，应该是不同的需求。写作文不能保留口语词，它是一篇优美的文章，但不是 AI 味，是人写的那种。」**

这份矩阵解决一件事：**先判文体，再决定改什么、改到什么程度。** 七个文体各有档案（另加润色改稿），通用原则写在 `SKILL.md`，本文件只做路由和对照。

## 一、先判文体，再动手

问三个问题：

1. **谁在读？他期待什么？**（阅卷人 / 读者 / 被通知的人 / 观众 / 熟人 / 潜在客户）
2. **场合多正式？能不能出现「我」、口语词、情绪？**
3. **信息必须精确到什么程度？改错了会不会出事？**

分流表：

| 文本在做什么 | 文体 | 去哪个档案 |
| --- | --- | --- |
| 表达感受、审美、立意思考，书面 | 作文 / 文学写作 | `01-作文与文学写作.md` |
| 传递观点、讲故事、让人读完 | 公众号 / 文章 | `02-公众号与文章.md` |
| 传递准确信息、要求可执行 | 通知 / 公告 | `03-通知与公告.md` |
| 面对镜头或麦克风说话 | 视频 / 音频口播 | `04-视频口播.md` |
| 跟熟人即时交流、短 | 朋友圈 / 聊天 | `05-朋友圈与聊天.md` |
| 说服购买、报名、使用 | 产品 / 课程文案 | `06-产品与课程文案.md` |
| 汇报工作、总结经验、反映情况、述职 | 报告 / 总结 | `08-报告与总结.md` |
| 只说了「润色一下」，没给场景 | 先判文体；判不出按 | `07-润色与改稿.md` |

判断依据：看原文的语体、发布渠道、称呼方式、是否需要回看。判不出时按「润色」处理，默认最小干预、不换文体。

## 三、通用底线（所有文体都成立）

1. **事实保真**：数字、日期、价格、承诺、引用不能动；不新增案例、来源、第一人称经历。
2. **文体一致**：作文不加语气词；通知不加梗；口播不念文章；聊天不成段说理。改完比原文更像「这个文体」，不是更像「随便一段话」。
3. **作者声音优先**：口癖、方言、个人节奏、惯用标点先进保护区。改写是拿掉 AI 腔，不是换成模型的声音。
4. **别改过头**：原文干净就说不用改；不为展示工作量硬改通顺句子。
5. **看密度，不看单次**：同一表达 200 字内出现 ≥3 次才动；单个出现先放过。
6. **篇幅 ±20%**：口播字数对应时长，删过头要补回信息。
7. **先结构，后句子，再词**：只换词通常不够，但结构也不要乱动，作文和通知尤其。
8. **交付报告按档位**：叙事 / 议论给命中清单 + 亮点保留 + 三行改动；功能类只给三行「改了什么、哪句保留」，不强制清单。
9. **合规前置**：考试、竞赛、毕业论文、评奖场景只做错别字 / 病句级提示，不做成段改写；不代写、不补经历、不帮规避 AI 检测。依据见 `research/deep/ai-policy.md`。
10. **官方文体先判**：官方评论、政务发布、公文、发言先按 `references/official-style.md` 的「四测试」判断排比 / 引用 / 金句 / 对仗是否保留，不套通用配额；公文格式、文种结语、政治规范表述见同文件 A/B/C 表，不默认当 AI 味。
11. **脚本之后还有第二层**：lint 只查表面；交付前按档位审稿——叙事类过 L2–L4 + 卡 A/B，议论类用卡 C+B，功能类走保真门禁 + 档案自检。脚本 0 分不等于过关。
12. **报告 / 总结：可信优先**：数据和口径（时间范围、同比 / 环比、来源、样本量）优先；问题不能虚化；下一步要有动作、责任人、时间、验收；报告不得夹带请示。
13. **示例不是素材**：档案里的「改后」示例（数字、人名、地点、经历）是演示内容，不是可复用事实；真实改写只能用原文 / 用户素材，缺的写 `【待补：…】`，不许照抄示例或补造。

## 四、最容易犯的五个错

- **把去 AI 味等于加口语**：作文、通知、公告加语气词是事故。
- **把人味等于随意**：通知里出现「哈」「咱们」会显得不专业。
- **把自然等于全拆短句**：通篇等长短句，也是另一种模板。
- **把润色等于重写**：用户只说润色时，默认最小干预，结构不动。
- **把口语等于错别字**：书面文案不刻意造错字；只有聊天、口播的手滑感可以适度保留。

## 五、使用方式

1. 用第一节三个问题判文体；
2. 读对应档案，取它的「人味标准 / AI 高危清单 / 保留清单 / 改写顺序」；
3. 通用规则（本文件第三节 + `SKILL.md` 硬门禁）照样生效；
4. 需要量化时跑 `scripts/ai_tell_lint.py`，按 `--genre` 选口播 / 书面 / 聊天 / 作文 / 通知 / 报告 / 政务；
5. 按档案第七节自检；
6. 交付时给报告，说明动了什么、故意保留什么。

**冲突处理**：具体文体档案优先于通用清单；档案没写的回退到 `SKILL.md`。

## 三·五、审稿分档（先判档，再选卡）

| 档位 | 文体 | 审稿方式 |
| --- | --- | --- |
| 叙事类 | 记叙文、散文、小说、公众号故事、口播故事 | L2–L4 + 卡 A 真实感 + 卡 B 文笔 |
| 议论类 | 议论文、评论、行业分析、观点文 | 卡 C（扣题 / 论点链 / 论据真实 / 分析 / 反驳 / 结论）+ 卡 B；不套卡 A |
| 功能类 | 通知 / 公告、聊天、产品文案、报告 / 总结 | 保真门禁 + 该档案第七节自检 + lint；不套叙事卡 |

详见 `references/review-layers.md`。

兜底：口播非故事类（知识、带货、资讯）按功能类；公众号 / 文章故事类按叙事、观点类按议论；演讲稿按主干判；判不清按功能类 + 档案自检，不套卡 A。

## 六、档案模板与维护

每份档案统一八节：适用场景与目标 / 人味标准 / AI 腔高危清单 / 保留清单 / 改写顺序与手法 / AI→人 对照 / 交付前自检 / 与相邻文体的边界。

规则来源标注约定：

- `[语料验证]`：lieflat 283 万字中文对照研究通过的特征（见 `references/ai-tells-cn.md` 第八节）；
- `[项目实践]`：从 GitHub 同类项目借鉴的方法（blader、Humanizer-zh、say-it-human、stop-slop 等，只借思路）；
- `[经验]`：本项目的写作经验，未做语料验证；
- `[公文惯例]`：通知、公告的格式与惯例，不能当 AI 味删掉。

维护节奏：模型风格会漂移，建议每半年用「同题生成 vs 人类样本」重测一次词表；新增文体时先写 5 组对照，再提炼规则，最后登记到本矩阵。
